# Подсветка кода BSL: сборка и тесты

Пакет oscript-md везёт в `src/highlight` всё, что нужно странице, чтобы раскрасить блоки
кода с языком `bsl` или `1c`: движок [shiki](https://shiki.style) с одной грамматикой BSL
(вместе с языком запросов внутри строк) и темой `css-variables`, скрипт, который находит
блоки и грузит движок, и цвета по умолчанию. Здесь движок собирают, а всю поставку
проверяют. Как подключить подсветку к странице — в [README библиотеки](../../README.md#подсветка-кода-bsl-в-браузере).

## Что куда уезжает

| Файл | Что это |
| --- | --- |
| `src/highlight/shiki-bsl.mjs` | движок: минифицированный ES-модуль с одной функцией `токены(код, язык)`; выход сборки |
| `src/highlight/shiki-bsl.LICENSE.txt` | лицензии всего, что вошло в движок, и происхождение грамматики BSL; выход сборки |
| `src/highlight/oscript-md-highlight.js` | скрипт: ванильный JS без сборки — находит блоки и грузит движок |
| `src/highlight/oscript-md-highlight.css` | цвета по умолчанию: переменные `--shiki-*`, светлые и пары `light-dark()` |

Движок и файл его лицензий в git не хранятся (они в `.gitignore`): их собирает
`npm ci && npm run build` здесь по `package-lock.json`. Пакет получает их при `opm build` —
хук `ПередСборкой` в `packagedef` зовёт сценарий `собрать.os`, и тот же сценарий зовут
`tasks/test.os` и `tasks/test_unit.os` до юнит-тестов. С чужого CDN движок не берётся:
страница может жить и в закрытом контуре, поэтому пакет везёт его с собой.

Текст лицензии грамматики BSL лежит здесь же, в `лицензия-грамматики-bsl.txt`: грамматика
приезжает внутри `@shikijs/langs-precompiled`, и своей лицензии у неё там нет.

## Сборка

```bash
cd tools/highlight
npm ci          # точные версии из package-lock.json
npm run build   # пишет shiki-bsl.mjs и shiki-bsl.LICENSE.txt в src/highlight
```

Для OneScript то же самое делает `собрать.os`: `ЗагрузитьСценарий(...).СобратьДвижок()`
проверяет, что в `PATH` есть node 20+, и запускает `npm ci --no-audit --no-fund` и
`npm run build` (на Windows — через `cmd /c`: npm там `npm.cmd`). Вывод npm идёт прямо
в лог. Если node нет или он старше 20-й версии, если npm не запустился или вернул
не ноль — сценарий бросает исключение с командой, каталогом и тем, чем она кончилась, и
`opm build` падает, не создав пакет. Сценарий обходится встроенными средствами OneScript 2.0:
при `opm build` в релизе dev-зависимостей пакета нет, а `packagedef` компилируется и до их
установки.

Для сборки нужны node 20+ с npm и доступ к реестру npm.

## Пределы

Код на странице может быть чужим, и раскрашивается он в главном потоке вкладки, поэтому
работа ограничена:

- строку от 1000 символов и длиннее движок не разбирает — она остаётся одним куском текста;
- над одной строкой грамматика думает не дольше 50 мс, дальше строка докрашивается как есть;
- блок длиннее 20 000 символов скрипт движку не отдаёт вовсе;
- блоки раскрашиваются по одному за задачу, и между ними вкладка отвечает;
- на всю страницу у движка 2 секунды работы: когда они потрачены, остальные блоки
  остаются текстом.

Первый разбор собирает грамматику, а это дольше предела на строку, поэтому движок
разогревается при загрузке: иначе первая строка на странице приходила бы бесцветной.

## Цвета по умолчанию

Движок пишет в цвет токена переменную (`var(--shiki-token-keyword)` и т. п.), значения
переменных задаёт лист `oscript-md-highlight.css`. На элементе с `data-md-highlight` у каждой
переменной светлое значение, а внутри `@supports (color: light-dark(#000, #fff))` — пара
`light-dark(светлое, тёмное)`. Тёмное браузер берёт, только если страница или элемент
объявили тёмную схему через `color-scheme`; тему системы лист сам не спрашивает, и
страница без `color-scheme` остаётся светлой.

Светлые значения взяты из темы shiki `github-light`, тёмные — из `github-dark`: у переменной
тот цвет, которым тема GitHub красит ту же область разметки (`keyword`, `string`, `comment`,
`constant`, `variable.parameter`, `markup.inserted`…), а пунктуация — цветом текста, как
у GitHub. Три переменные тема css-variables собирает из разнородных областей, и для них
взят цвет того, что они красят в BSL или что обозначают: `--shiki-token-string-expression` —
цвет строк (в BSL она красит строковые литералы), `--shiki-token-function` — цвет имён
функций (`entity.name.function`), `--shiki-token-link` — цвет ссылок (`string.other.link`).

## Обновить shiki

Обновления приходят сами: dependabot (`.github/dependabot.yml`) раз в неделю предлагает PR —
все `@shikijs/*` одной группой, esbuild, linkedom и postcss — другой. CI этого PR собирает
движок с новыми версиями на всех системах и гоняет все тесты; зелёный PR можно вливать.

Руками — так же:

1. Поднять версии `@shikijs/*` в `package.json` — точными, без `^`, все четыре одинаковыми.
2. `npm install` — обновит `package-lock.json`.
3. `npm test`. Если у темы css-variables появилась новая переменная, тест стилей её назовёт:
   значение нужно добавить в лист дважды — светлое из `github-light` и пару `light-dark()`
   с тёмным из `github-dark`.
4. Закоммитить `package.json` и `package-lock.json`; движок соберётся из них сам.

## Тесты

```bash
npm test        # сначала npm run build, потом node --test
```

Они же идут в CI джобом «Подсветка кода» и стерегут четыре вещи:

- `движок.test.js` — собранный движок размечает BSL: ключевые слова, константы, строки,
  комментарии, запрос внутри строки, псевдоним `1c`; текст из токенов собирается без потерь,
  строка длиннее предела не разбирается, а первая строка холодного движка — разбирается;
- `скрипт.test.js` — скрипт в DOM (linkedom) раскрашивает только блоки `bsl` и `1c` внутри
  `[data-md-highlight]`, по одному за задачу и в пределах бюджета времени; без таких блоков
  движок не грузит, блок длиннее предела ему не отдаёт, отказ движка оставляет код
  текстом, а разметка из кода не исполняется;
- `стили.test.js` — у каждой переменной, которую тема может выдать токену, на
  `[data-md-highlight]` есть светлый цвет и пара `light-dark()`, начатая с него; других
  правил, в том числе по теме системы, в листе нет, и страницу он сам не красит;
- `сборка.test.js` — две сборки из одного `package-lock.json` дают одни и те же байты, а файл
  лицензий называет каждый пакет, вошедший в движок, и происхождение грамматики.

Что скрипт ищет тот самый атрибут, который называет `MarkdownПодсветка.ИмяАтрибута()`,
стережёт юнит-тест OneScript `tests/unit/подсветка-test.os`: он запускает скрипт и движок
пакета в node над маленькой страницей из `tests/unit/страница-с-подсветкой.mjs`.

Нужен node 20+: предкомпилированная грамматика пользуется флагом регулярных выражений `v`,
а тесты — `node:test`. Движок лежит файлом `.mjs`, поэтому node грузит его модулем без
распознавания синтаксиса.

## Браузеры

Предкомпилированные регулярные выражения грамматики используют флаг `v`: Chrome 112+,
Firefox 116+, Safari 17+. В более раннем браузере движок не загрузится, и код останется
обычным текстом: подсветка — только улучшение, страница без неё та же. Тёмные значения
через `light-dark()` понимают Chrome 123+, Firefox 120+ и Safari 17.5+; браузер между этими
версиями и версиями движка раскрашивает код светлой палитрой.
